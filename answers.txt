/******************************************************************************
** 1. Describe how your firstIndexOf() method in RangeBinarySearch.java
**    finds the first index of a key that equals the search key.
******************************************************************************/
The method performs a binary search on the sorted array. It keeps two bounds,
low and high, for the part of the array that may still contain the answer. At
each iteration, it compares the middle element with the key. If the middle
element is smaller than the key, the answer must be to the right, so low is
moved to middle + 1. If it is larger, the answer must be to the left, so high
is moved to middle - 1. If it is equal, middle is saved as the current best
answer, but the search continues in the left half by setting high to middle - 1.
Continuing left after a match is what guarantees that the returned index is the
first equal element. If no equal element is found, result remains -1.


/******************************************************************************
** 2. What is the worst case time complexity in the number of compares
**    that each of the operations in the Autocomplete data type make,
**    as a function of the number of terms n and the number of matching terms m?
******************************************************************************/

sortDictionary():  O(n log n)

The constructor calls Arrays.sort on the whole dictionary with
byLexicographicOrder. Object arrays are sorted with a merge sort, which does
about n log n comparisons in the worst case, and every one of those comparisons
is a call into the comparator, where the two words are compared with
compareToIgnoreCase. It runs once, when the Autocomplete object is created.


allMatches():  O(log n + m log m)

Two binary searches find the first and last dictionary positions whose first
k characters equal the prefix, using O(log n) comparisons. The matching range
contains m terms. Copying the range takes O(m) time, and sorting those terms by
reverse weight takes O(m log m) comparisons. The total is O(log n + m log m),
which is at least as large as the O(m) copying cost.

numberOfMatches():  O(log n)

Two binary searches find the first and last matching positions. Each search
uses O(log n) comparisons, and the method returns last - first + 1. It does
not scan or sort the m matching terms, so its running time does not depend on m.

/******************************************************************************
** B. Are there any known bugs / limitations?
******************************************************************************/

All three files compile with javac and every required method is done. What is 
worth knowing is that the comparators use compareToIgnoreCase. That handles upper
and lower case, but it still orders characters by their Unicode values, so accented 
letters do not land where a reader of that language expects for example in nordsamiska.txt 
the letter á should sit right after a, but it compares as greater than z, so those words 
collect at the end of the list.

/******************************************************************************
** D. Describe any serious problems you encountered.                    
******************************************************************************/
The first problem was the leftmost index. We wrote firstIndexOf like the ordinary search
from the notes, returning as soon as it found something equal. For whole words it
looked fine, because cities.txt has no repeated words. It broke the moment we used
the prefix comparator, where a whole row of terms compares equal, so the index we
got back was from somewhere in the middle of that row. allMatches then copied from
there to the end and quietly dropped everything before it. Three equal words and a
print statement is what finally showed it.

The second was speed. Our allMatches sorted the whole dictionary by weight and then
picked the matches out of it, which is n log n work on every search. In the GUI it
made typing sluggish on gp2011.txt, since every key press runs a search. We changed
it to copy the block of matches out first and sort only that.
